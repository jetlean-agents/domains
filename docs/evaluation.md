## Оценка домена (этап 3)

Конвейер оценки (`src/evaluation/pipeline.ts`) берёт домен, собирает сигналы из
Wayback Machine (CDX + выборка снимков) и Common Crawl, считает балл 0–100,
подбирает нишу и выставляет флаги. Результат кэшируется в таблице
`domain_evaluations` на `EVAL_CACHE_TTL` секунд (по умолчанию 30 дней).

### Источники

**Wayback (`src/evaluation/wayback.ts`).** Глобальная очередь
(`src/evaluation/rate-queue.ts`, `MinIntervalQueue`) держит не больше одного
запроса на `WAYBACK_MIN_INTERVAL_MS` (по умолчанию `4000` мс, ≈15
запросов/мин — выше archive.org в практике блокирует IP) — это касается и
CDX-запросов списка снимков, и скачивания самих снимков, вместе, а не по
отдельности.

**Очередь и cooldown.** На каждую попытку запроса (успешную и неуспешную)
очередь пишет одну строку лога:

```
queue=<wayback|cc> t=<ms> gap_ms=<с прошлого запроса> status=<код|error> attempt=<n>
```

`gap_ms` — реальный интервал с начала предыдущего запроса в этой очереди
(неважно, какой домен или вызов); при соблюдении лимита должен быть
`>= WAYBACK_MIN_INTERVAL_MS` / `>= CC_MIN_INTERVAL_MS`. На 429/503 очередь
**целиком** встаёт на cooldown — не только вызов, который получил 429, а
вообще все следующие `acquire()` любого вызова в этой очереди, иначе
параллельный job по другому домену продолжил бы бить archive.org в обычном
темпе, пока первый «пережидает» свой локальный backoff (это и было причиной
бага: конкурирующие job'ы совместно выбивали более жёсткую блокировку по IP).
Длительность cooldown — `Retry-After` от upstream, если есть, иначе минимум
60 с; при повторных 429/503 удваивается (60с → 2мин → 4мин → 8мин → …),
потолок 15 минут. Строка лога при входе в cooldown:

```
queue=<wayback|cc> cooldown=1 ms=<длительность> status=<429|503> consecutive=<n>
```

Прочие 5xx — обычный retryable-повтор (до 3 раз) без входа в cooldown; любой
другой не-200/404(CC) статус — не повторяется, ошибка сразу всплывает в
job (чтобы временная блокировка никогда не кэшировалась как «нет истории»).

1. `fetchCdx` — два **хостовых** запроса (без `matchType=domain`, который
   тянет вообще все URL всех поддоменов — слишком тяжело для старого `.com`):
   `web.archive.org/cdx/search/cdx?url=<domain>&output=json&collapse=timestamp:6`
   и такой же для `www.<domain>`, результаты объединяются и дедуплицируются
   по `(timestamp, original)` (`buildCdxUrl`/`mergeCdxRows`). `collapse=timestamp:6`
   схлопывает снимки до одного в календарный месяц — для годовой выборки
   этого достаточно, и выборка снимков идёт по главной странице хоста, а не
   по случайным глубоким URL. Если запрос по `www.` не удался после всех
   повторов — используется история только по голому хосту (не теряем уже
   полученный результат).
2. `summarizeSnapshots` — первый/последний снимок, число снимков по годам,
   `age_years` (возраст с первого снимка).
3. `pickSampleSnapshots` — выбирает до `WAYBACK_SAMPLE` снимков, по одному на
   отдельный год, равномерно распределённых от самого старого до самого
   нового года.
4. `fetchSnapshotContent` — скачивает «сырой» (`id_`) HTML каждого выбранного
   снимка; язык и тематика определяются по ключевым словам
   (`src/evaluation/keywords.ts`, RU/UA/EN), спам/дорвей/PBN — по отдельному
   списку ключевых слов (казино, фарма, adult, иероглифический спам), парковка
   — по типовым фразам (GoDaddy/Sedo/Afternic: «this domain is for sale»,
   «domain parking» и т.п.).

**Common Crawl (`src/evaluation/commoncrawl.ts`).** Та же схема очереди,
интервал `CC_MIN_INTERVAL_MS`.

> **Честное ограничение.** Задача просила «ссылки» — число ссылающихся
> доменов и топ анкоров. Common Crawl Index API физически не умеет отвечать
> на вопрос «кто ссылается на этот домен» — это может дать только host-level
> web graph, который распространяется только целиком (многогигабайтные
> Parquet/edge-list файлы на S3), что выходит за рамки этой задачи и бюджета
> Contabo. Поэтому вместо истинных backlinks мы используем **дешёвую замену**:
> число страниц самого домена, попавших в последний индекс Common Crawl
> (`url=*.domain`, лимит 1000 строк на запрос) — это сигнал «присутствия» /
> популярности в вебе, а не backlink-граф. `backlinks_method` в ответе API
> всегда явно называет метод (`cc_index_page_count`), чтобы не выдавать это
> за точные backlinks. `top_anchors` по той же причине всегда пустой массив —
> якорный текст ссылок Index API не возвращает вовсе.

### Балл (0–100)

`src/evaluation/score.ts`, чистые функции без побочных эффектов:

| Компонент | Максимум | Формула |
|---|---|---|
| `age` | 20 | `min(20, age_years * 2)` — 10 лет истории = максимум |
| `history` | 20 | `min(20, years_covered * 2 + min(10, snapshot_count / 5))` — и широта (разные годы), и глубина (число снимков) |
| `cleanliness` | 25 | `25 - spam_sample_ratio*20 - (parked_latest ? 5 : 0) - (topic_change ? 5 : 0)`, не ниже 0 |
| `backlinks` | 20 | `min(20, log2(backlinks_estimate + 1) * 3)` — логарифмическая шкала |
| `domain_shape` | 10 | по длине второго уровня домена (`example` в `example.com.ua`): ≤6 → 10, ≤10 → 8, ≤15 → 5, иначе 2; минус 2 за цифры, минус 2 за дефис |
| `zone` | 5 | `.com` → 5, `.com.ua` → 4, `.ua`/`.net` → 3, `.org` → 2, прочие известные → 1 |

Итог — сумма компонентов, зажатая в `[0, 100]`.

### Ниша

`.auto | energy | news | deals_us | none`. Для каждого сэмпла считаются
попадания по словарям `NICHE_KEYWORDS` (RU/UA/EN), суммируются по всем
сэмплам, добавляется небольшой приор по зоне (`ZONE_NICHE_PRIOR`:
`.ua`/`.com.ua` → auto/energy/news, `.com` → deals_us). Побеждает ниша с
максимальной суммой; `confidence` — доля победителя от суммы по всем нишам
(0 если ни одно ключевое слово не нашлось и приора по зоне нет — тогда
niche=`none`).

### Флаги

- `no_history` — нет ни одного снимка Wayback.
- `spam` — хотя бы один из проанализированных сэмплов содержит спам-ключевые
  слова (казино/фарма/adult/CJK-спам).
- `parked` — последний (самый новый) проанализированный сэмпл — типовая
  парковочная страница.
- `topic_change` — доминирующая ниша отличается между сэмплами (сэмплы без
  явной ниши игнорируются, чтобы один неоднозначный снимок посреди истории не
  создавал ложный срабатывание).

### Кэш и лимиты

- `domain_evaluations.cache_expires_at` — `EVAL_CACHE_TTL` секунд после
  вычисления; `GET /api/v1/evaluate/:id` и `GET /api/v1/evaluations` отдают
  сохранённый результат без повторного похода во внешние сервисы.
- Фоновая автооценка новых дропов (`src/evaluation/auto-eval.ts`, cron
  `EVAL_CRON`) обрабатывает домены дропов без свежей оценки, не больше
  `EVAL_DAILY_LIMIT` свежих вычислений в календарные сутки (UTC); счётчик —
  таблица `auto_eval_daily_counts`.

### API

- `POST /api/v1/evaluate` — тело `{ "domains": [...] }`; входные домены
  нормализуются (punycode, lowercase) и дедуплицируются **до** создания job
  (`normalizeDomainList` в `src/routes/evaluate.ts`) — и в `evaluation_jobs`,
  и в ответе всегда уже нормализованный список, без дублей и сырого ввода.
  До 20 уникальных доменов после нормализации; асинхронно создаёт
  `evaluation_jobs`, обработка в фоне, ответ `202 { job_id, status, domains }`.
- `GET /api/v1/evaluate/:id` — статус и результаты job (`pending | running |
  done | error`).
- `GET /api/v1/evaluations?domain=a.com,b.com` — читает уже сохранённые
  оценки из БД (без новых запросов к Wayback/Common Crawl); на этом эндпоинте
  фронтенд ничего не ждёт — страница домена и лента дропов используют именно его.
- `GET /api/v1/drops` — новые фильтры `niche=`, `min_score=`, `min_age=`,
  `sort=score` (сортировка по баллу вместо даты дропа по умолчанию).

### Известное ограничение (backlog, не блокирует)

`evaluation_jobs.status` переходит `pending → running → done|error` только
через код приложения; если процесс перезапускается, пока job в `running`
(например, рестарт деплоя во время долгого Wayback-прогона), запись
остаётся `running` навсегда — никто не переводит её обратно. На практике не
страшно (job создаётся заново по новому запросу, старая запись просто висит
в истории), но `GET /api/v1/evaluate/:id` для такой записи будет вечно
отдавать `running`. Следующий шаг — либо таймаут по `created_at` на чтении
(трактовать `running` старше N минут как зависший), либо помечать
незавершённые job'ы `error` при старте приложения.

### Тесты

Моки внешних сервисов: формула балла и классификатор нишы/спама тестируются
как чистые функции на фикстурах `test/fixtures/wayback/*.html` (сохранённые
HTML-снимки для каждой ниши + спам/parked-страница) без единого сетевого
запроса; `parseCdxResponse`/`buildCdxUrl`/`mergeCdxRows` — на фикстуре
`test/fixtures/wayback/cdx-sample.json` и синтетических рядах;
`MinIntervalQueue` — на искусственных задержках и кастомных (маленьких)
cooldown-границах, чтобы не ждать реальные 60с/15мин в тестах; отдельно
`computeCooldownMs` — чистая функция эскалации cooldown с настоящими
дефолтами (60с → … → 15мин), без таймеров вообще. `normalizeDomainList` —
нормализация/дедуп доменов для `POST /api/v1/evaluate`. Переиспользование
имени токена после revoke проверено как
регрессионный тест на содержимое миграции (`0003_evaluation.sql`) и ручным
прогоном на dev-стенде (создать → отозвать → создать то же имя снова) —
полноценный интеграционный тест на реальном Postgres не входит в `npm test`
(проект этого этапа и предыдущих тоже не делает запросов к БД в unit-тестах).
